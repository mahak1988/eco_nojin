## Why the prior BLOCKED ledger is invalid

`engine/reports/data/stage41c_blocked_records.jsonl` contains five entries, all marked `NOT_EXECUTED_ENV`. Its five IDs (`1`, `141`, `297`, `619`, `1209`) overlap IDs present in the shard output; those rows are `COMPUTED`. The file therefore does not account for any of the 640 no-result IDs and cannot be counted as a valid blocked ledger.

## Data and cache evidence

- The source Excel file exists and contains 1,722 test-district record IDs; this rules out missing record metadata for the 640 unprocessed IDs.
- `engine/reports/data/stage38_cache.sqlite` exists but contains **0 cache entries**.
- All 1,082 current result rows report `cache_hits = 0`.
- Consequently, there is no captured external weather/satellite input cache to replay deterministically for missing IDs. An execution now would have to reacquire live external inputs and could not establish Stage 40 input parity.

## Failure diagnosis

The single persisted failed result is:

| record_id | failure_reason | Classification |
|---|---|---|
| 1533 | `cannot access local variable 'baseline_predicted_yield' where it is not associated with a value` | Runner code bug |

The source is `engine/hydroma/eval/resumable_benchmark_runner.py`, in `process_record`: `baseline_predicted_yield` is read when building the result but is only assigned in the successful baseline branch or its local exception handler. When the outer HYRUE branch fails first, the variable is uninitialized. This is a concrete runner defect, not missing source data.

## Re-run decision

No benchmark/model rerun was performed. This audit was read-only against the shards, and the reusable input cache is empty. Re-running missing records against live APIs would create a new, potentially different input basis and would not close the Stage 40 comparability gap. A controlled future rerun should first persist the resolved input arrays and provenance per record, then rerun only the missing IDs with an explicit run manifest.

## Classification verdict

The 640 records cannot honestly be called `BLOCKED` with individual causes from the current artifacts. Their dataset rows are available, but their external inputs are not cached; 8 were left `RUNNING`, and 632 were not started. Accordingly, **there is no valid 1,308-record BLOCKED classification**. Current accounting is `COMPUTED 1081 + FAILED 1 + RUNNING 8 + UNSTARTED 632 = 1722`.
